# Introduction

Pourquoi le web sémantique en muséologie ?

???
Le web sémantique transforme radicalement la manière dont nous documentons, partageons et interconnectons les informations patrimoniales. Au-delà de l'aspect technique, c'est une nouvelle façon de penser la documentation des collections.

Les technologies du web sémantique et l’approche du web de données liées désignent une combinaison de techniques d’outils et de standards qui permettent de transformer le world wide web d’un web de documents à un web de données. Lorsque cette approche est appliquée au monde des bibliothèques, des archives et des musées, les données liées transforment la manière dont nous pouvons découvrir, analyser, et visualiser les contenus culturels et scientifiques.

Les données ouvertes et liées (Linked Open Data LOD) permettent aux institutions patrimoniales et culturelles de publier et partager des informations sur leur collections en ouvrant d’infinies possibilités de réutilisations et d’enrichissements et afin d’augmenter leur visibilité.

Cependant, les acteurs du monde culturels sont confrontés à plusieurs enjeux dans l’appropriation de ces technologies :

- bien sûr, l’adoption de ces technologies et de ces standards nécessite des compétences techniques particulières. Pour autant, ce n’est pas le seul enjeu pour les institutions ou les acteurs du secteur culturel.
- En effet, partager les données des collections suppose l’adoption de politiques d’ouverture de données adaptées
- cette démarche présente également des enjeux relatifs à l’autorité des institutions. Dans un contexte distribué, il y a un changement d’échelle qui n’est pas sans impact sur les collection.

### Syntaxe des URI

```
  foo://example.com:8042/over/there?name=ferret#nose
  \_/   \_________/ \__/ \________/ \_________/ \__/
   |         |        |       |          |        |
  scheme authority   port    path      query    fragment       
```

séparateurs : `:`, `/`, `?`, `#`, `[`, `]`, `@`
sous-séparateurs : `!`, `$`, `&`, `'`, `(`, `)`, `*`, `+`, `,`, `;`, `=`

- **URL** – Uniform Resource Locator ([RFC1738](https://tools.ietf.org/html/rfc1738))
  - unique identification and location of resources
  - *mailto:name@umontreal.ca*
- **URN** – Uniform Resource Name ([RFC2141](https://tools.ietf.org/html/rfc2141))
  - location-independent resource identifier
  - *urn:isbn:0-83891251-6*
- **URI** – Uniform Resource Identifier ([RFC3986](https://tools.ietf.org/html/rfc3986))
  - union of URLs and URNs
- **IRI** – Internationalized Resource Identifiers ([RFC3987](https://www.ietf.org/rfc/rfc3987))
  - Non-ASCII chars don’t need to be encoded.

???

Les IRI sont des identifiants, ceux-ci peuvent être signifiants ou noms. 

Bonnes pratiques : 

- Veiller à la persistance des différentes parties qui composent l’IRI
- Choisir un système de nommage extensible et pérenne
- Garantir l’unicité, en excluant toute ambiguïté

Plusieurs manière de gérer les identifiants

- utilisation de systèmes normalisés (DOI, URN, ARK)
- utilisation d’IRI et mise en place de règles de gestion (une problématique d’organisation qui nécessite des processus et des moyens)
- prévoir les cas de disparition ou de fusion de ressources

### Du web de documents au web de données

#### Web de documents (traditionnel)
- Liens entre pages web via des hyperliens
- Contenu principalement destiné aux humains
- Navigation par exploration

#### Web de données (sémantique)
- Liens entre données structurées
- Contenu compréhensible par les machines
- Requêtes précises et intégration de données

???

**Le web classique** lie des **documents** entre eux via des hyperliens.

**Le web sémantique** lie des **données** entre elles via des relations explicites.

**Différence clé :**
- Web de documents : "Cliquez ici pour en savoir plus sur Marie-Antoinette"
- Web de données : `<oeuvre:001> <créateur> <personne:marie-antoinette>` (relation machine-readable)

---
### Le modèle REST

Le web sémantique s'appuie sur l'architecture REST (Representational State Transfer) :
- **Resources** : Tout ce qui peut être nommé (une œuvre, un artiste, un lieu)
- **Representations** : Différentes façons de représenter une ressource (HTML pour humains, RDF pour machines)
- **Identifiers** : URI uniques pour identifier sans ambiguïté

**Négociation de contenu :**
La même URI peut renvoyer différents formats selon qui demande :
- Un navigateur → page HTML
- Une application → données RDF/XML ou JSON-LD

## Rappel RDF : Le modèle de données

### Le principe fondamental : les triplets

RDF (Resource Description Framework) structure l'information en **triplets** :

**Sujet — Prédicat — Objet**

**Exemple :**
```
<La_Joconde> <a_pour_créateur> <Léonard_de_Vinci>
<La_Joconde> <est_conservée_à> <Musée_du_Louvre>
<Léonard_de_Vinci> <est_né_en> "1452"
```
???
Pensez-y comme des phrases simples que vous assemblez pour construire une description complète.

---
### Les éléments d'un triplet

**Le Sujet** : Toujours un URI
- Identifie la ressource que vous décrivez
- Exemple : `http://votremusee.org/oeuvres/portrait_001`

**Le Prédicat** : Toujours un URI
- Exprime la relation ou la propriété
- Exemple : `http://purl.org/dc/terms/creator` (créateur selon Dublin Core)

**L'Objet** : Peut être un URI ou un littéral
- URI : `http://votremusee.org/personnes/vestier_antoine`
- Littéral : `"Portrait de Marie-Antoinette"@fr`

---
### Syntaxe Turtle (Terse RDF Triple Language)

Turtle est la notation la plus lisible pour RDF :

```turtle
@prefix crm: <http://www.cidoc-crm.org/cidoc-crm/> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

<http://votremusee.org/objet/001> a crm:E22_Human-Made_Object ;
    rdfs:label "Portrait de Marie-Antoinette"@fr ;
    crm:P108_has_produced <http://votremusee.org/production/001> .

<http://votremusee.org/production/001> a crm:E12_Production ;
    crm:P14_carried_out_by <http://votremusee.org/personne/vestier> ;
    crm:P4_has_time-span <http://votremusee.org/timespan/001> .
```

**Raccourcis syntaxiques :**
- `;` pour partager le même sujet
- `,` pour partager sujet et prédicat
- `a` est un raccourci pour `rdf:type`

---
### Les graphes RDF

Les triplets forment un **graphe** où :
- Les nœuds sont les sujets et objets
- Les arcs sont les prédicats

**Avantage du graphe :**
- Pas d'ordre imposé (contrairement à XML)
- Pas de hiérarchie rigide
- Facilite l'intégration de sources hétérogènes

## Ontologies

> "Une ontologie est une spécification formelle explicite d'une conceptualisation partagée."
> — Thomas R. Gruber

Une ontologie définit les **classes** (types d'entités), les **propriétés** (relations) et les **règles** d'un domaine de connaissances.

**Différence avec un vocabulaire contrôlé classique :**
- Vocabulaire contrôlé : Liste de termes préférés (ex: thésaurus)
- Ontologie: + définitions formelles + relations explicites + règles logiques

---
### CIDOC-CRM : L'ontologie de référence

**Le CIDOC Conceptual Reference Model** est LA norme internationale (ISO 21127) pour le patrimoine culturel.

---
#### Principes fondamentaux

**Approche événementielle**
Au lieu de dire simplement "Van Gogh a peint Les Tournesols", CIDOC-CRM décrit l'**événement de création** avec tous ses paramètres.

**Exemple en CIDOC-CRM :**
```turtle
<oeuvre:tournesols> a crm:E22_Human-Made_Object ;
    crm:P108_was_produced_by <event:production_tournesols> .

<event:production_tournesols> a crm:E12_Production ;
    crm:P14_carried_out_by <personne:van_gogh> ;
    crm:P7_took_place_at <lieu:arles> ;
    crm:P4_has_time-span <timespan:1888> .
```
---

**Classes principales**

- **E21_Person** : Une personne (artiste, collectionneur, donateur)
- **E22_Human-Made_Object** : Un objet créé par l'humain (l'œuvre elle-même)
- **E53_Place** : Un lieu (atelier, lieu d'exposition, provenance)
- **E52_Time-Span** : Une période temporelle
- **E12_Production** : L'événement de création
- **E8_Acquisition** : L'événement d'acquisition
- **E11_Modification** : Une restauration, une modification

---

## SPARQL : Interroger les Données Liées

SPARQL est le **langage de requête standardisé** pour interroger des données RDF. Il permet de formuler des questions complexes sur des graphes de données.

---
### Structure d'une requête SPARQL

```sparql
PREFIX crm: <http://www.cidoc-crm.org/cidoc-crm/>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

SELECT ?oeuvre ?titre ?artiste
WHERE {
  ?oeuvre a crm:E22_Human-Made_Object ;
          crm:P102_has_title ?titre ;
          crm:P108i_was_produced_by ?production .
  ?production crm:P14_carried_out_by ?artiste .
  ?artiste rdfs:label "Léonard de Vinci"@fr .
}
```
---
### Utilisation

- **Recherche avancée** : Trouver toutes les œuvres d'un artiste produites à une période donnée
- **Analyse de collection** : Statistiques sur les techniques, matériaux, provenances
- **Recherche fédérée** : Interroger simultanément plusieurs musées
- **Enrichissement** : Identifier les liens avec des ressources externes
